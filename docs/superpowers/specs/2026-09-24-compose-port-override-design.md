# Publishing a site's port for it

Date: 2026-09-24. Status: approved in chat.

## Problem

Since the port allocation work (`2026-09-23-site-port-allocation-design.md`), hostd writes the port the
admin chose into the environment's `.env` as `<portEnv>` (default `WEB_PORT`), then refuses unless the
repo's compose file publishes it:

```
invalid-project: no service publishes port 5002; publish ${WEB_PORT} in the compose file, like "127.0.0.1:${WEB_PORT}:3000"
```

Most repos do not say that. They hard code a port (`"3000:3000"`), read their own variable, or publish
nothing at all. backroom, the case that raised this, publishes:

```yaml
ports:
  - "${BIND_ADDR:-127.0.0.1}:${PORT:-3001}:${PORT:-3001}"
```

It reads `PORT`, not `WEB_PORT`, so it resolves to `127.0.0.1:3001:3001` and the create is refused. The
only fix today is a commit to the client's repo.

Editing the compose file on the dedi does not work: every deploy checks out a fresh tree, and the
checkout's copy of a file always wins (`carryComposeFiles` in `hostd/src/agent/deploy.ts`).

## Goal

- The port set in the panel is the only host port a site publishes, whatever its repo's compose file says.
- Every other service in the site stays reachable only inside the site's own compose network.
- No change to the client's repo, and no step for the admin to remember: this happens for every
  environment hostd provisions, with no option to turn it off.

## The override file

hostd owns one compose file per environment, `hostd.ports.yml`, in the environment's folder, listed last
in that environment's compose list in the registry, so compose merges it over the repo's own files. For
backroom it would read:

```yaml
# Written by hostd. The port is set in the portal; do not edit this file.
services:
  "backroom":
    ports: !override ["127.0.0.1:${WEB_PORT}:3001"]
```

A site with a database as well:

```yaml
services:
  "web":
    ports: !override ["127.0.0.1:${WEB_PORT}:3000"]
  "db":
    ports: !reset []
```

- `!override` replaces the service's whole `ports` list instead of merging into it, so a hard-coded
  mapping in the repo cannot also claim a host port. `!reset []` removes every host port from a service.
  Both need Compose 2.24 or later; the agent runs v5.1.4 and the dedi v5.1.3.
- The port stays in `.env` (the `${<portEnv>}` reference), so a port change rewrites `.env` exactly as it
  does today, and the override file itself only changes when the site's services do.
- Always `127.0.0.1`: Apache is the only thing that should reach a site, and a repo's own `BIND_ADDR`
  style setting stops having any effect.
- Services still reach each other by service name on their container ports (`mongo:27017`), since that
  is the compose network and not a published port. Nothing inside a site changes.

## Building it

`hostd/src/agent/port-override.ts`, pure apart from its callers passing in the resolved compose:

`portOverride(resolved: ResolvedCompose, guessed: Record<string, GuessedService>, portEnv: string)`
answers `{ ok: true, text: string, service: string, target: number }` or `{ ok: false, problem: string }`.

- **The resolved compose** is `docker compose config` over the repo's own files only, the environment's
  compose list without `hostd.ports.yml`, run after `.env` has the chosen port in it. So `${PORT:-3001}`
  and the like are already resolved to what the repo would run with.
- **The web service** is the one service `guessRole` calls `site`. With several, the ones that publish a
  port or have an `expose` entry are preferred; if that still leaves more than one (or none), it refuses:
  `hostd cannot tell which service is the site (web, worker); give the others an image it recognises as a
  database, or publish a port from the site's service only`.
- **The container port** is the `target` of the web service's first TCP entry in `ports`, in the order
  the file lists them. With no `ports`, the first entry in its `expose`. With neither, it refuses:
  `web does not say which port it listens on; add expose: ["3000"] (the port inside the container) to it
  in the compose file`. `ResolvedService` gains `expose?: Array<string | number>`.
- **A web service with `network_mode: host`** is refused: `web uses network_mode: host, so hostd cannot
  choose its port; remove network_mode from it`. A host-network service ignores `ports`.
  `ResolvedService` gains `network_mode?: string`.
- **Every other service** that has a `ports` list gets `ports: !reset []`. A service with no `ports` is
  left out of the file.
- Service names are written as quoted YAML keys, and the whole file is built as text (the tags are not
  worth teaching the `yaml` library to emit).

Tests on fixtures: a hard-coded mapping, backroom's `${PORT:-3001}`, `expose` only, no port at all,
several site services with one publishing, several with none, a database that publishes 27017, a
`network_mode: host` web service, and a UDP entry listed before the TCP one.

## Where it runs

**Create and add-environment** (`provisionOnDisk` in `hostd/src/agent/provision.ts`). After the clone,
`afterClone` and `setPortEnv`, and before `owner` and `own` so the new file is owned with the rest:

1. Resolve the repo's own files (the list the form sent, or `docker-compose.yml`).
2. `portOverride`. A refusal rolls back the whole create, as a compose failure does today.
3. Write `hostd.ports.yml` into the environment's folder.
4. The environment's compose list becomes the repo's list plus `hostd.ports.yml`, and that full list is
   what `resolve` checks and what the registry records. For add-environment the test entry records its
   own compose list rather than inheriting live's, since the two folders each have their own file.

The existing "some service publishes the port" check stays, run against the merged list, as the last
line of defence: after the override it can only fail if the override is wrong.

**Port change** (`hostd/src/agent/port-change.ts`). An environment already listing `hostd.ports.yml`
needs nothing new: `.env` changes and the override picks it up. One that does not (a site enrolled by
hand, or created before this) gets the file the same way as a create, written after `setPortEnv` and
before the `published` check. The `set-port` registry change gains an optional `compose` list, so the
port and the new compose list are one registry write. The undo removes the file again.

**Deploy** (`hostd/src/agent/deploy.ts`). For an environment listing `hostd.ports.yml`, a new step after
`carryComposeFiles` rebuilds the file in the new tree from the new checkout's own files, instead of
using the carried copy. So a commit that adds a service publishing a host port, or moves the web
service's container port, is covered at that deploy, not at the next port change. A refusal fails the
deploy before anything is built, with the same messages as a create, and the running site is untouched.
An environment without `hostd.ports.yml` in its list deploys as it does today.

## Limits and portal copy

- The registry and protocol keep `MAX_COMPOSE_FILES` at 8, counting `hostd.ports.yml`. The New site form
  allows 7 of its own (`app/(portal)/portal/newSite/schema.ts`), and refuses a file named
  `hostd.ports.yml`: `hostd.ports.yml is the file hostd writes; name your own compose files`.
  `hostd/src/shared/protocol.ts` refuses the same name on a create.
- `notPublishedProblem` stays for the final check, but no longer tells the admin to edit the compose
  file, since hostd did that: `hostd could not publish port 5002 (its override did not take effect); check
  hostd.ports.yml in /var/www/<id>`.
- New site port hint (`NewSite.tsx`): `The port the site listens on. hostd publishes it to the site's
  service on 127.0.0.1, whatever the compose file says.`
- The create's reply names what hostd chose, so the admin sees it: `published 5002 to backroom:3001`.

## Not in this

- Rewriting existing sites that are not moved. They get the file at their next port change.
- Choosing the web service or container port in the portal. The refusals say what to add to the compose
  file; a picker can follow if that turns out to be common.
- Ranges and UDP. hostd publishes one TCP port per environment, as before.
